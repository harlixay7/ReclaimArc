# SpaceExtract — Testing

## Running the suite

```
cargo test --workspace
```

Expect:
- platform: 6 tests (real Windows sparse integration)
- journal: 8 tests
- archive: 19 tests
- core: 21 tests + 12 fault-injection integration tests

## Fault-injection harness (the heart)

`crates/core/tests/fault_injection.rs` simulates process death at **every
durable transition** by running the engine in a child process with
`SPACEEXTRACT_FAULT_AT=<point>`; the child dies with exit code 86 at the
requested point. The parent then:

1. asserts the child died at the exact point,
2. asserts per-point invariants (unit not committed / finals adoptable /
   intent persisted / source still allocated, …),
3. runs `prepare_resume` + the engine to completion,
4. verifies every output is byte-identical to the fixture data,
5. (destructive mode) verifies source allocation measurably dropped and the
   journal records all ranges RECLAIMED.

Crash points: after-partial-write, after-output-flush, after-rename,
after-journal-commit, before-hole-punch, during-hole-punch,
before-reclaimed-commit.

Also covered: DoD #4 (low-space extraction succeeds where normal extraction
fails — the free-space observation is injected, see below), path-traversal
rejection, pause→resume completion, and source-modification detection.

## Test-only free-space hook

`SPACEEXTRACT_TEST_FREE_SPACE` replaces the free-space observation when the
`test-hooks` feature is enabled (dev builds only). This lets integration
tests exercise low-space scenarios deterministically; it is not a faked
result — the planner, engine and reclamation all run their real logic
against it, and reclamation is still verified against the real filesystem
allocation.

## Real Windows integration tests

- sparse-capable temp file → mark sparse → reclaim a middle range → verify
  allocated size drops (measured via `FSCTL_QUERY_ALLOCATED_RANGES`) and
  every byte outside the range is unchanged, every byte inside reads zero;
- volume capability probe leaves no probe file behind;
- fixture archives (RAR4 and RAR5, solid, multipart, corrupt, truncated)
  are generated byte-exactly by the fixture writer; the header parser is
  cross-validated against the official decoder's own header stream.

## Property tests

- the space planner: any plan marked feasible never dips below the reserve
  under an independent re-simulation; infeasible plans always carry a
  precise reason;
- the recovery-unit state machine: every transition is linear and legal.

## Fuzzing

- path validation is fuzz-adjacent via property-style coverage of hostile
  names (absolute, traversal, ADS, device names, control chars, collisions);
  the archive header parser bounds every read and rejects malformed input
  rather than panicking (no unwraps on archive input — audit-gated).

## Known limitation

Encrypted-archive fixtures cannot be synthesized by the fixture writer
(implementing RAR encryption is out of scope); encrypted paths are exercised
through the decoder integration and require real corpus files when available.
